# 010 · 移除临时无 SNI 后备

- 日期：2026-09-29。

## 发现了什么

此前部分 H@H 图片节点在携带 SNI 的正常 TLS 握手中返回无效数据，触发
`WRONG_VERSION_NUMBER`；去掉 SNI 后却能正常握手并通过证书验证。因此在
[008](008-temporary-tls-compatibility.md) 中加入了独立、可移除的无 SNI 后备连接。

后续发现，Xfinity Advanced Security / CyberSecure 的域名拦截也会产生相同
类型的 TLS 异常。用户在 Magpie 域名上验证了关闭该功能后连接立即恢复，
这为此前 H@H 的 SNI 相关故障提供了新的解释：兼容层可能绕过的是网络路径上的
域名拦截，而不是修复服务器的 TLS 兼容性。

在用户报告关闭 CyberSecure 后，重新检查近期使用日志并在 Android 上测试：

- 日志中的两个完整下载任务均完成，缓存复用和有界重试正常发挥作用，
  未发现新的缓存或下载回归证据。
- 最近失败过的 81 个主机/端口中，47 个使用正常 SNI 即可通过证书验证并完成
  TLS/HTTP 通信；六个早期故障节点固定原 IP 后也全部通过。
- 其余 33 个主机无法解析，另一个节点在正常 SNI 和无 SNI 下均失败，
  没有发现当前仍只有无 SNI 才能连通的节点。
- 论坛 403 和少量连接超时仍然存在，是独立问题，不属于本次移除兼容层所解决的范围。

这些结果支持 CyberSecure 拦截的解释，但没有对 H@H 做即时开关对照，不能把
历史根因写成完全证实。根路径测试验证的是 TLS/HTTP 通信，不等于实际图片下载；
无法解析的样本也不算 TLS 验证通过。

## 为什么改

无 SNI 后备本来就是针对特定故障的临时措施。正常握手恢复后，继续保留另一套
Java/OkHttp 传输、平台通道和流式会话，会增加维护成本，却没有当前测试证据
证明仍有必要。剩余的 DNS 或节点可用性问题也不能靠去掉 SNI 解决。

因此删除整个专用 fallback，而不是只关闭开关、留下闲置实现。缓存复用、
有界重试和换源仍能处理普通网络故障，有独立价值，不随兼容层一起回滚。

## 改了什么

- 删除 Android 无 SNI 后备连接及 Dart 平台桥接、原生流式会话。
- 删除 MainActivity 中对应的注册和回收逻辑，以及兼容层专用的显式 OkHttp 依赖。
- 删除 `FE_IMAGE_SNI_COMPAT` 开关、兼容事件和专用桥接测试。
- 图片传输只使用正常 TLS 路径；失败后交给原有有界重试和换源流程，
  不再额外发起无 SNI 连接，并为这一行为补充回归测试。
- 保留 `FE_IMAGE_FAST_FAILOVER`、按端点和代理隔离的短时避让、缓存优先、
  手动恢复、取消与超时，以及已完成文件的保留逻辑。
- 不改变原图语义、代理配置或既有证书策略，不迁移数据库或清空缓存。

当前端点恢复规则见 [维护指南](reference/image-endpoint-compatibility.md)。
