## 为什么改

验证后的功能不能长期只存在于工作区或测试分支。与此同时，历史原因散落在
提交信息、少量文档和本机记录中，后续容易分不清为什么改、哪些是临时措施，
以及“保全了备份代码”是否等于“主 App 已包含备份功能”。

## 做了什么

1. 确认待提交源码与已安装版本的源文件摘要一致，先保存已验证的实现。
2. 以两个独立的非快进合并提交，将 `fix/handshake-recovery` 和
   `fix/reader-cache-representation` 合入 `master`，保留可追溯的分支边界。
3. 核对合并后的代码树与实现提交一致，没有在合并时额外改变已验证的功能。
4. 建立 `docs/change-log/`，按每次改动补齐问题、实现、设计取舍、验证和后续状态。
5. 将已有四份维护指南移入 `reference/`，原路径只保留指引；补收录备份分支文档
   快照，但不合并备份功能代码。
6. 在中英文 README 中加入入口，以后每次改动继续补充编号记录。

## 为什么这样做

保留原实现提交和两个 merge commit，方便以后定位、比较或撤回临时兼容层，
而不是把所有历史压扁成一次无法追踪的大改动。历史条目和当前维护指南分开：
前者不改写过去的验证结论，后者反映目前实际行为。

文档只采用可以核实的 Git、测试/构建记录和用户反馈。没有文档的历史改动根据
提交补齐，不宣称此前每次都已有完整设计文档。
