# 003 · 自动补页保留缓存、元数据与脱敏诊断

- 日期：2026-09-16。
- 提交：`e60f444491a8b78fd33c9082bfc6e24cd5a5545e`。
- 分支：`fix/reuse-reader-cache`；已包含在主干。

## 为什么改

初版缓存复用后，用户仍观察到重复传输和个别页面长时间不完成。
自动补页/刷新过期地址的 `reDownload` 路径仍可能绕过缓存；恢复任务和更新
缩略图列表时，也可能丢掉先前已经解析出的图片地址、换源信息等元数据。

仅凭下载速度或界面转圈无法区分“真的在传图”“只在解析页面”与“缓存查找失败”，
因此需要能关联阅读和下载的诊断证据。

## 改了什么

- 把自动重试中的 `reDownload` 解释为“需要刷新地址”，不再等同于“禁止缓存”。
  初次下载、自动补页和 403 恢复都先查缓存。
- 合并缩略图列表时保留已有的已解析字段；恢复任务时不重建已完成的数据库行。
- 在真正传输前保存解析出的源信息，传输失败后仍能再次定位缓存和换源。
- 正确处理 Executor 的错误，不把失败页当成完成页。
- 新增可选择开启的 JSONL 诊断，记录缓存键指纹、阶段、页状态和网络结果；
  单份约 1 MiB，加一个轮转文件，禁止保存完整 URL、Cookie、标题等。

## 为什么这样做

刷新链接和丢弃缓存是两件事。网络节点或临时 URL 的问题不应导致已经取得的
图片被重新下载，更不应重置整本的完成进度。

诊断采用固定字段和容量上限，而不是打开全量 HTTP 请求/响应日志：
既能解释重复请求，又减少签名地址、登录信息和作品信息泄露的风险。

## 验证与边界

当时 **55 项回归测试**通过，另有负向对照：恢复旧行为后，34 页任务中
失败页重试产生重复传输的测试会失败。

该阶段没有改变 TLS 信任策略、archive 流程或数据库结构，也没有宣称解决
远端握手故障。随后停滞监控被更明确的逐页有界恢复替代，见 [006](006-bounded-handshake-recovery.md)。

当前诊断字段和使用方式见 [维护指南](reference/download-cache-diagnostics.md)。
